## 0. Назначение changelog

`CHANGELOG.md` отвечает только на вопрос:

> **Что в проекте изменилось, почему это было принято и на что повлияло?**

Он не является:

- текущим описанием проекта — актуальные решения находятся в `PROJECT.md`;
- спецификацией интерфейсов — актуальные контракты находятся в `CONTRACTS.md`;
- списком текущих задач — статусы находятся в `ROADMAP.md`;
- копией Git history;
- протоколом всей переписки с ИИ;
- хранилищем отвергнутых идей и черновых вариантов.

`CHANGELOG.md` помогает человеку или ИИ-агенту понять, **почему текущее решение отличается от прежнего**, не перечитывая старые чаты и архивные документы.

---

## 1. Когда запись обязательна

Запись добавляется, если принято хотя бы одно из изменений:

- изменено назначение или границы проекта;
- изменена архитектура или ответственность модулей;
- изменён неизменяемый инвариант;
- выбран или заменён элемент технологического стека;
- добавлена или удалена существенная зависимость;
- изменён внешний или внутренний контракт;
- изменена версия JSON/YAML-схемы;
- добавлен, удалён или переименован статус, enum или поле;
- изменена модель риск-оценки, полноты или critical override;
- изменена политика безопасности, хранения или очистки;
- изменена граница MVP;
- принято решение по ранее `OPEN`-вопросу;
- отложенная функция перенесена в MVP или наоборот;
- завершён значимый релиз или этап, меняющий доступные возможности;
- исправлена ошибка, которая меняла смысл результата или безопасность.

---

## 2. Когда запись не нужна

Changelog обычно не обновляется при:

- исправлении опечатки;
- форматировании Markdown;
- переименовании локальной переменной без изменения поведения;
- добавлении обычного unit-теста к уже зафиксированному поведению;
- рефакторинге без изменения контракта и архитектуры;
- обновлении чекбокса текущей задачи — это делает `ROADMAP.md`;
- промежуточном коммите;
- обсуждении идеи, которая ещё не принята;
- временной локальной отладке;
- изменении комментария в коде без смыслового изменения.

Если изменение не влияет на будущего разработчика, пользователя, контракт, безопасность или способ эксплуатации, записи, скорее всего, не требуется.

## 3. Главный порядок обновления документов

При принятом изменении документы обновляются в следующем порядке:

1. определить владельца актуальной информации;
2. изменить `PROJECT.md` или `CONTRACTS.md`;
3. обновить задачи/статус в `ROADMAP.md`, если изменение влияет на план;
4. добавить запись в `CHANGELOG.md`;
5. проверить отсутствие противоречий между документами;
6. изменить код и тесты либо, если изменение возникло из реализации, убедиться, что код и документация уже синхронизированы.

`CHANGELOG.md` никогда не должен быть единственным местом, где записано актуальное решение.

Пример:

- в changelog написано, что выбран асинхронный API;
- в `CONTRACTS.md` должны быть обновлены маршруты и статус решения;
- в `ROADMAP.md` должен быть снят соответствующий блокер.

## 4. Формат разделов

### 4.1. Верхний раздел `Unreleased`

Все принятые, но ещё не вошедшие в оформленный релиз изменения сначала записываются в раздел:

```markdown
## [Unreleased]
```

При выпуске версии записи переносятся под заголовок версии:

```markdown
## [0.1.0] — 2026-08-15
```

До появления программного релиза допускаются только датированные проектные записи.

### 4.2. Категории

Используются категории:

- **Added** — добавлена новая возможность, документ или контракт;
- **Changed** — изменено существующее решение или поведение;
- **Fixed** — исправлена ошибка в поведении, контракте или безопасности;
- **Removed** — удалена возможность, зависимость или контракт;
- **Deprecated** — решение пока работает, но будет удалено;
- **Security** — изменение, связанное с безопасностью;
- **Decision** — принято важное проектное решение по открытому вопросу.

Необязательно использовать все категории в каждой записи.

### 4.3. Содержание пункта

Хороший пункт отвечает минимум на три вопроса:

1. что изменено;
2. почему;
3. какое последствие для проекта.

Рекомендуемый формат:

```markdown
- **[Область] Краткое изменение.** Причина: ... Влияние: ...
```

Для крупного решения допускается расширенный формат:

```markdown
### Decision

- **[API] Выбран асинхронный job-style профиль.**
  - Причина: анализ видео может превышать безопасное время одного HTTP-запроса.
  - Влияние: добавляются операции создания задачи, получения статуса и результата.
  - Обновлены: `CONTRACTS.md`, `ROADMAP.md`.
  - Миграция: синхронный маршрут не реализуется в MVP.
```

## 5. Правила качества записи

### 5.1. Запись должна быть конкретной

Плохо:

```markdown
- Улучшена архитектура.
```

Хорошо:

```markdown
- **[Storage] Запись результата вынесена за интерфейс ResultRepository.** Причина: возможность позднее заменить JSON-файлы на SQLite без изменения модулей анализа.
```

### 5.2. Записывается принятое решение, а не процесс размышлений

Плохо:

```markdown
- Думали использовать Redis, потом Celery, потом решили пока посмотреть.
```

Хорошо:

```markdown
- **[Queue] Внешний брокер исключён из MVP.** Причина: локальному прототипу достаточно внутренней очереди, а Redis/Celery преждевременно усложняют установку.
```

### 5.3. Не дублировать весь актуальный текст

Плохо: вставлять полную JSON Schema в changelog.

Хорошо:

```markdown
- **[Schema] В AnalysisResult добавлен блок completeness.** Подробная структура зафиксирована в `CONTRACTS.md`, schema version повышена до 1.1.
```

### 5.4. Не переписывать историю задним числом

Если старая запись оказалась ошибочной:

- не удалять её молча;
- добавить новую запись, отменяющую или уточняющую решение;
- при очевидной опечатке допускается исправление без отдельного пункта.

### 5.5. Использовать абсолютные даты

Используется формат:

```text
YYYY-MM-DD
```

Не использовать «сегодня», «вчера», «на прошлой неделе».

### 5.6. Не записывать секреты и внутренние данные

Запрещено включать:

- токены;
- пароли;
- реальные пути пользователей;
- содержимое анализируемых файлов;
- персональные данные;
- внутренние детали инцидента, не нужные проектной истории.

## 6. Версионирование проекта

До первого работающего прототипа рекомендуется использовать:

```text
0.x.y
```

Пример:

- `0.1.0` — первый сквозной каркас;
- `0.2.0` — базовые реальные анализаторы;
- `0.3.0` — WebUI/API и результат;
- `1.0.0` — согласованный стабильный MVP, если критерии действительно выполнены.

Правила SemVer:

- `MAJOR` — несовместимое изменение публичного контракта;
- `MINOR` — новая обратно совместимая возможность;
- `PATCH` — обратно совместимое исправление.

Версия программного продукта и `schema_version` JSON связаны, но не обязаны совпадать.

## 7. Инструкция для ИИ-агента

После выполнения задачи агент должен проверить:

1. изменилось ли принятое поведение;
2. изменился ли контракт;
3. изменился ли стек или зависимость;
4. изменилась ли безопасность или хранение;
5. разрешён ли `OPEN`-вопрос;
6. изменена ли граница MVP.

Если ответ «да» хотя бы по одному пункту:

- обновить актуальный документ владельца области;
- добавить changelog-запись;
- назвать затронутую область;
- указать причину и влияние;
- при контрактном изменении указать версию схемы;
- при миграции указать необходимые действия.

Если изменён только статус выполнения:

- обновить `ROADMAP.md`;
- changelog не нужен, если это не релиз или значимая поставка возможности.

## 9. Контрольный пример

### Плохая запись

```markdown
- Добавили API и немного поменяли файлы.
```

Недостатки:

- непонятно, какой API;
- нет причины;
- нет влияния;
- неясно, принят ли контракт;
- невозможно понять миграцию.

### Хорошая запись

```markdown
- **[API] Добавлен асинхронный маршрут создания анализа `POST /api/v1/analyses`.** Причина: видеообработка может быть дольше времени безопасного HTTP-ожидания. Влияние: клиент получает `analysis_id` и запрашивает статус отдельно; обновлены `CONTRACTS.md` и контрактные тесты.
```

- **[Cleanup] Ошибка удаления не скрывается.** Допускается ограниченный карантин только для повторной очистки, а не для штатного хранения исходников.

## 10. Краткое правило

```text
Текущее решение — в PROJECT.md или CONTRACTS.md.
Текущая работа — в ROADMAP.md.
Причина изменения — в CHANGELOG.md.
```

Если один и тот же полный текст оказался записан в двух документах, почти наверняка нарушена граница ответственности.
