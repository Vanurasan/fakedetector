# PROJECT.md

> Единое описание проекта инструмента обнаружения признаков искусственного создания или модификации мультимедийных файлов.
>
> Версия документа: **1.0**  
> Дата фиксации: **2026-07-24**  
> Статус: **базовый источник истины для разработки**

## 0. Назначение и статус документа

`PROJECT.md` предназначен для быстрого восстановления полного проектного контекста человеком или ИИ-агентом перед разработкой.

Документ фиксирует:

- назначение и границы системы;
- принятые архитектурные решения;
- функциональную структуру;
- основные потоки обработки;
- правила формирования результата;
- политику безопасности и хранения;
- технологический стек первой версии;
- ограничения и открытые вопросы;
- обязательные правила работы ИИ-агента.

Документ **не должен** дублировать:

- подробные структуры HTTP-запросов, ответов, JSON и YAML — они принадлежат `CONTRACTS.md`;
- этапы, чек-листы и текущее состояние реализации — они принадлежат `ROADMAP.md`;
- историю изменений — она принадлежит `CHANGELOG.md`.

### 0.1. Обозначения статуса решений

В документе применяются четыре статуса:

- **FIXED** — решение принято и не меняется без явного согласования владельца проекта;
- **CONDITIONAL** — подход принят предварительно, но его применение зависит от условий реализации;
- **OPEN** — решение ещё не принято;
- **EXAMPLE** — проектный пример, который нельзя автоматически считать окончательным требованием.

### 0.2. Источники истины

Каждый документ отвечает только за свою область:

| Документ | Единственная зона ответственности |
|---|---|
| `PROJECT.md` | Назначение, границы, архитектура, стек, политики и инварианты |
| `CONTRACTS.md` | Внешние и внутренние интерфейсы, модели данных, схемы и ошибки |
| `ROADMAP.md` | Этапы, задачи, статусы, критерии завершения и ближайшая работа |
| `CHANGELOG.md` | История принятых изменений и причины изменений |

Исходная курсовая работа и прежние файлы `AI_HANDOVER`, `PROJECT_MEMORY`, `ARCHITECTURE`, `API`, `TECH_STACK` и старая версия `ROADMAP` являются архивными источниками. После принятия настоящего документа они используются для справки, но не должны переопределять его решения.

При противоречии применяется правило владельца области:

- архитектурное решение определяется `PROJECT.md`;
- формат данных или интерфейс определяется `CONTRACTS.md`;
- статус реализации определяется `ROADMAP.md`;
- `CHANGELOG.md` объясняет изменение, но не заменяет актуальное решение.

### 0.3. Минимальный контекст для ИИ-агента

Перед выполнением задачи агент должен прочитать:

1. `PROJECT.md`;
2. текущий этап и связанные задачи в `ROADMAP.md`;
3. только относящиеся к задаче разделы `CONTRACTS.md`.

`CHANGELOG.md` читается только при необходимости восстановить причину изменения.

## 1. Краткое описание проекта

### 1.1. Назначение

Система предназначена для предварительного автоматизированного анализа мультимедийных файлов на признаки:

- искусственного создания;
- редактирования;
- монтажа;
- подмены содержимого;
- синтетической речи;
- подмены лица, мимики или видеоряда;
- аудиовизуальной несогласованности.

Поддерживаемые группы входных данных:

- изображения;
- аудиофайлы;
- видеофайлы.

Основной прикладной сценарий — проверка мультимедийных вложений электронной почты, способных использоваться в фишинге, компрометации деловой переписки и атаках социальной инженерии.

При этом ядро анализа не привязано к электронной почте и может принимать мультимедийные файлы из других внешних систем через API.

**Статус: FIXED.**

### 1.2. Результат работы

Система не устанавливает юридически или экспертно подтверждённый факт подделки.

Результатом является **риск-оценка**, включающая:

- итоговый уровень риска;
- числовую оценку, если она предусмотрена активной моделью оценки;
- сведения о выявленных признаках;
- пояснение факторов, повлиявших на результат;
- сведения о полноте анализа и ошибках анализаторов;
- рекомендацию по дальнейшим действиям.

Вероятность подделки может включаться только при наличии определённого и проверенного способа её расчёта. Она не должна выдумываться, копироваться из максимального `confidence` отдельного анализатора или механически выводиться из суммы баллов.

**Статус риск-ориентированного результата: FIXED.**  
**Формула итоговой вероятности: OPEN.**

### 1.3. Место системы в защите организации

Инструмент является дополнительным компонентом защиты и поддержки принятия решения.

Он не заменяет:

- антивирус;
- песочницу для вредоносных файлов;
- антифишинговый шлюз;
- DLP;
- SIEM;
- SOAR;
- почтовый сервер;
- систему электронной почты;
- экспертную цифровую криминалистику;
- процедуру расследования инцидентов.

**Статус: FIXED.**

## 2. Предметная область и проблема

### 2.1. Угроза

Мультимедийное вложение может быть опасно не наличием исполняемого вредоносного кода, а недостоверностью содержания.

Файл может использоваться для:

- имитации документа или его фрагмента;
- создания ложного визуального подтверждения события;
- имитации голоса руководителя, сотрудника или контрагента;
- передачи синтетического голосового распоряжения;
- создания видеообращения с подменой лица, мимики или речи;
- усиления убедительности фишингового сообщения;
- поддержки мошеннического или манипулятивного сценария.

### 2.2. Основной предметный сценарий

1. В организацию поступает сообщение или файл из внешнего канала.
2. Сообщение содержит изображение, аудио или видео.
3. Файл может не содержать вредоносного программного кода.
4. Опасность может заключаться в искусственно созданном или модифицированном содержании.
5. Пользователь или внешний компонент передаёт файл в инструмент.
6. Инструмент выполняет предварительную проверку и специализированный анализ.
7. Система формирует объяснимую риск-оценку.
8. Пользователь или внешняя система принимает дальнейшее решение.

### 2.3. Основные ограничения достоверности

Качество результата зависит от:

- разрешения изображения или видео;
- длительности аудио или видео;
- степени сжатия;
- повторного кодирования;
- шумов;
- освещения;
- наличия и качества лица в кадре;
- сохранности метаданных;
- формата и кодека;
- применимости конкретного анализатора;
- качества и актуальности ML-модели;
- соответствия входных данных обучающей выборке модели.

Система не может гарантировать обнаружение всех существующих и будущих методов генерации или модификации мультимедиа.

**Статус: FIXED.**

## 3. Цели, границы и исключения

### 3.1. Цели первой версии

Первая версия должна продемонстрировать полный управляемый цикл:

1. приём мультимедийного файла;
2. безопасную первичную проверку;
3. определение типа медиа;
4. создание и сопровождение задачи анализа;
5. временное размещение файла;
6. предварительную обработку;
7. запуск подходящих анализаторов;
8. преобразование результатов анализаторов в признаки;
9. формирование риск-оценки;
10. формирование машиночитаемого и человекочитаемого результата;
11. обработку частичных сбоев;
12. удаление исходных и промежуточных данных;
13. сохранение служебного результата и технического журнала.

### 3.2. Поддерживаемые входные данные

Базовая область анализа:

- `image`;
- `audio`;
- `video`.

Файл должен передаваться на анализ напрямую.

Допустимые расширения и лимиты задаются конфигурацией. Окончательный перечень утверждается в `CONTRACTS.md` и конфигурационной схеме.

Проектные примеры начальных ограничений:

| Тип | Форматы-кандидаты | Максимальный размер |
|---|---|---:|
| Изображения | JPEG, PNG, WebP | 20 МБ |
| Аудио | WAV, MP3, FLAC, M4A | 50 МБ |
| Видео | MP4, MOV, AVI, MKV | 200 МБ |

Эти значения имеют статус **EXAMPLE** и могут быть скорректированы после проверки оборудования и нагрузки.

### 3.3. Что не входит в базовую версию

Без отдельного решения система не должна:

- распаковывать архивы;
- рекурсивно обходить архивы;
- извлекать мультимедиа из офисных документов;
- извлекать мультимедиа из PDF;
- анализировать документы как самостоятельный тип данных;
- анализировать произвольные контейнеры со вложенными объектами;
- хранить исходные мультимедийные файлы долговременно;
- выдавать бинарный вердикт «подделка / не подделка»;
- автоматически блокировать письмо или пользователя;
- самостоятельно принимать юридически значимые решения;
- разрабатывать новую фундаментальную ML-модель с нуля как обязательную часть MVP;
- строить микросервисную или распределённую инфраструктуру заранее;
- реализовывать почтовый коннектор раньше базового ядра;
- реализовывать SIEM/DLP/SOAR-интеграции раньше стабильного API.

**Статус: FIXED.**

## 4. Пользователи и каналы взаимодействия

### 4.1. Пользователь WebUI

Назначение:

- вручную выбрать и загрузить поддерживаемый файл;
- получить статус обработки;
- просмотреть человекочитаемый результат;
- увидеть ошибки, ограничения и рекомендации.

Ограничения:

- допускаются только разрешённые типы и размеры файлов;
- пользовательский доступ должен предусматривать аутентификацию;
- конкретная модель пользователей и ролей определяется перед реализацией защищённого доступа.

### 4.2. Внешняя система через API

Назначение:

- автоматически передать файл;
- передать доступные сведения об источнике;
- получить машиночитаемый результат.

Возможные внешние системы:

- почтовый коннектор;
- почтовый шлюз;
- SIEM;
- DLP;
- SOAR;
- корпоративное хранилище;
- система документооборота;
- мессенджер;
- другая система обмена файлами.

Требования:

- API использует токен доступа;
- в MVP допускается статический токен из переменной окружения;
- конкретные маршруты, методы, форматы ответов и коды ошибок определяются в `CONTRACTS.md`.

### 4.3. Специалист по информационной безопасности

Назначение:

- интерпретировать результат;
- выполнить ручную проверку;
- запросить подтверждение по независимому каналу;
- передать материал в процедуру расследования.

Инструмент поддерживает решение специалиста, но не заменяет его.

### 4.4. Почтовый коннектор

Почтовый коннектор:

- является внешним компонентом;
- извлекает поддерживаемые вложения из электронной почты;
- передаёт файл ядру через API;
- может передавать идентификатор письма, отправителя и другие сведения источника;
- не входит в базовое ядро анализа;
- не реализуется первым.

**Статус архитектурной границы: FIXED.**

## 5. Архитектурные принципы

### 5.1. Модульность

Система строится как модульный монолит первой версии.

Модули должны иметь чёткие зоны ответственности и взаимодействовать через типизированные внутренние контракты.

Отдельные анализаторы должны подключаться, отключаться и заменяться без переработки:

- WebUI;
- API;
- приёма файлов;
- маршрутизации;
- риск-оценки;
- формирования результата.

**Статус: FIXED.**

### 5.2. Разделение внешнего слоя и ядра

WebUI и API являются внешними адаптерами.

Они не должны содержать бизнес-логику анализа.

HTTP-маршрут должен:

1. принять запрос;
2. проверить параметры уровня транспорта;
3. вызвать прикладной сервис;
4. преобразовать результат или ошибку в HTTP-ответ.

Анализаторы и риск-оценка не должны зависеть от FastAPI.

**Статус: FIXED.**

### 5.3. Набор анализаторов вместо универсального детектора

Для разных типов медиа применяются разные группы методов.

Один универсальный детектор не является основой системы.

Причины:

- разные модальности имеют разные признаки подделки;
- один метод не покрывает все типы манипуляций;
- качество ML-моделей зависит от данных и сценария;
- объединение независимых признаков повышает объяснимость.

**Статус: FIXED.**

### 5.4. Конфигурируемость

Конфигурация управляет:

- каналами доступа;
- лимитами;
- форматами;
- валидацией;
- временным хранением;
- предварительной обработкой;
- активными анализаторами;
- параллельностью;
- правилами риск-оценки;
- формированием результата;
- обработкой ошибок;
- журналированием;
- внешними интеграциями.

Секреты не хранятся в конфигурации, включённой в Git.

**Статус: FIXED.**

### 5.5. Минимальная инфраструктура

Первая версия должна использовать минимально необходимое количество инфраструктурных компонентов.

Не добавлять технологию «на будущее». Она подключается только при наличии подтверждённой проблемы, которую нельзя разумно решить текущим стеком.

**Статус: FIXED.**

## 6. Логические компоненты системы

### 6.1. WebUI

Ответственность:

- отображение формы загрузки;
- передача файла прикладному слою;
- отображение состояния;
- отображение результата и ошибок.

Не отвечает за:

- анализ файла;
- расчёт риска;
- прямую запись результатов;
- управление ML-моделями.

### 6.2. API

Ответственность:

- программный приём файла;
- проверка токена;
- приём доступных сведений об источнике;
- вызов прикладного сервиса;
- возврат машиночитаемого результата или статуса.

Точная синхронная или асинхронная модель взаимодействия имеет статус **OPEN** и должна быть зафиксирована в `CONTRACTS.md` до реализации соответствующих маршрутов.

### 6.3. Модуль приёма данных

Ответственность:

- единая точка входа после WebUI/API;
- присвоение `analysis_id`;
- регистрация начала обработки;
- передача файла на первичную проверку;
- фиксация канала поступления.

### 6.4. Модуль первичной проверки

Обязательные проверки:

1. наличие файла;
2. максимальный размер;
3. расширение;
4. MIME-тип;
5. фактическая сигнатура;
6. соответствие заявленного и фактического типа;
7. возможность безопасного декодирования или чтения;
8. расчёт SHA-256;
9. проверка поддерживаемой группы медиа.

Неподдерживаемый, повреждённый или несоответствующий файл отклоняется до запуска анализаторов.

### 6.5. Модуль маршрутизации

Ответственность:

- определить `image`, `audio` или `video`;
- выбрать маршрут предварительной обработки;
- выбрать допустимую группу анализаторов;
- отклонить неподдерживаемый тип.

### 6.6. Модуль управления задачами

Ответственность:

- сопровождать жизненный цикл задачи;
- управлять очередью;
- ограничивать параллельность;
- фиксировать время начала и завершения;
- координировать предобработку, анализаторы, очистку и результат;
- гарантировать выполнение завершающей очистки, насколько это технически возможно.

Первая версия использует внутренний механизм приложения, без внешнего брокера.

### 6.7. Временное хранилище

Ответственность:

- хранить исходный файл только на период анализа;
- хранить нормализованные копии и промежуточные данные;
- изолировать данные разных `analysis_id`;
- применять TTL;
- удалять данные после обработки;
- фиксировать результат очистки.

### 6.8. Предварительная обработка

Предобработка подготавливает данные, но не выносит итоговое заключение.

Для изображений:

- извлечение метаданных;
- безопасное декодирование;
- нормализация рабочей копии;
- получение технических параметров.

Для аудио:

- извлечение метаданных;
- декодирование;
- нормализация частоты дискретизации при необходимости;
- разбиение на фрагменты;
- построение спектральных представлений;
- получение технических параметров.

Для видео:

- извлечение параметров контейнера и потоков;
- извлечение метаданных;
- выбор или извлечение ключевых кадров;
- извлечение аудиодорожки;
- подготовка временных сегментов;
- передача кадров визуальным анализаторам;
- передача аудиодорожки аудиоанализаторам.

### 6.9. Модуль управления анализаторами

Ответственность:

- зарегистрировать доступные анализаторы;
- определить их совместимость с типом медиа;
- учитывать включение и отключение через конфигурацию;
- запускать анализаторы через единый контракт;
- изолировать сбой отдельного анализатора;
- собирать длительность, статус, ошибки и результаты;
- не позволять анализаторам напрямую формировать итоговый риск.

### 6.10. Анализаторы

Анализатор является самостоятельным компонентом, проверяющим одну группу признаков.

Он должен:

- объявлять идентификатор и версию;
- объявлять поддерживаемые типы входа;
- проверять применимость;
- принимать типизированные подготовленные данные;
- возвращать типизированный результат;
- не изменять исходный файл;
- не записывать итоговый отчёт напрямую;
- не присваивать окончательный уровень риска;
- корректно сообщать `not_applicable`, ошибку или успешный результат согласно контракту.

Точные модели данных и статусы определяются в `CONTRACTS.md`.

### 6.11. Модуль формирования признаков

Ответственность:

- преобразовать результаты анализаторов в нормализованные признаки;
- сохранить связь признака с источником;
- определить группу и серьёзность;
- сохранить локализацию, если она доступна;
- исключить неконтролируемое двойное суммирование связанных признаков;
- передать признаки модулю риск-оценки.

### 6.12. Модуль риск-оценки

Ответственность:

- агрегировать признаки;
- учитывать серьёзность;
- учитывать качество и применимость источника;
- учитывать согласованность независимых методов;
- рассчитать балльную оценку, если модель включена;
- определить уровень риска;
- применить critical override при выполнении утверждённых условий;
- учесть полноту анализа;
- подготовить объяснение результата.

Модуль риск-оценки не выполняет повторный анализ мультимедийного файла.

### 6.13. Модуль рекомендаций

Ответственность:

- сформировать дальнейшее действие на основе итогового риска и полноты анализа;
- использовать осторожные формулировки;
- не подменять решение специалиста.

Возможные рекомендации:

- дополнительная ручная проверка;
- подтверждение по альтернативному каналу;
- передача в расследование;
- повторный анализ более полным набором методов;
- отсутствие автоматических действий при недостаточной полноте анализа.

### 6.14. Модуль формирования результата

Ответственность:

- собрать единую модель результата;
- сформировать JSON-представление;
- предоставить данные WebUI;
- включить ошибки и предупреждения;
- включить сведения о полноте анализа;
- включить статус удаления временных данных;
- не дублировать бизнес-логику риск-оценки.

### 6.15. Репозиторий результатов

Прикладные модули не должны самостоятельно записывать JSON-файлы в разных местах.

Используется абстракция:

```text
ResultRepository
```

Минимальные операции первой версии:

```text
save(result)
get(analysis_id)
exists(analysis_id)
list_recent(limit)
```

Первая реализация:

```text
JsonFileResultRepository
```

### 6.16. Журналирование

Технический журнал предназначен для диагностики, а не для хранения результата анализа.

Он фиксирует события, длительность, статусы и ошибки без сохранения содержимого мультимедиа.

### 6.17. Конфигурация

Ответственность:

- загрузить YAML;
- объединить несекретные параметры и переменные окружения;
- проверить конфигурацию моделями Pydantic;
- прекратить запуск при критически некорректной конфигурации;
- предоставить типизированные настройки модулям.

### 6.18. Обработка ошибок

Ответственность:

- классифицировать ошибки;
- отделять отклонённый файл от внутреннего сбоя;
- изолировать сбой анализатора;
- обеспечить очистку через завершающий блок обработки;
- формировать безопасное сообщение пользователю;
- сохранять диагностические сведения без секретов и содержимого файла.

## 7. Канонический жизненный цикл анализа

### 7.1. Общий поток

1. WebUI или API получает файл.
2. Создаётся `analysis_id` и контекст источника.
3. Файл помещается в контролируемую рабочую область настолько, насколько это требуется для безопасной потоковой проверки.
4. Выполняются ограничения размера, расширения, MIME-типа и сигнатуры.
5. Выполняется безопасное чтение или декодирование.
6. Рассчитывается SHA-256.
7. Определяется тип медиа.
8. При нарушении правил задача завершается как отклонённая, анализаторы не запускаются.
9. Допустимая задача поступает в внутреннюю очередь обработки.
10. Выполняется предварительная обработка по типу медиа.
11. Запускаются включённые и применимые анализаторы.
12. Ошибки отдельных анализаторов фиксируются; остальные анализаторы продолжают работу, если это безопасно и возможно.
13. Результаты анализаторов преобразуются в признаки.
14. Рассчитывается риск и полнота анализа.
15. Формируются пояснение и рекомендация.
16. Формируется черновая модель итогового результата.
17. В завершающей секции удаляются исходные и промежуточные файлы.
18. В результат записывается фактический статус очистки.
19. Итоговый JSON сохраняется атомарно через `ResultRepository`.
20. Технические события записываются в журнал.
21. Результат возвращается WebUI или API.

Логический запрет: специализированные анализаторы не должны запускаться до успешного прохождения первичной проверки.

### 7.2. Недопустимый файл

Если файл не поддерживается или нарушает ограничения:

- анализ не выполняется;
- риск подделки не рассчитывается;
- возвращается результат невозможности обработки или ошибка валидации;
- временные данные удаляются;
- причина отклонения фиксируется безопасным образом.

Отклонение файла нельзя интерпретировать как высокий или низкий риск подделки.

### 7.3. Ошибка отдельного анализатора

Если один анализатор завершился с ошибкой:

- ошибка фиксируется;
- другие анализаторы продолжают работу, если это возможно;
- итоговый результат помечается как неполный, если ошибка снижает покрытие;
- отсутствие признака от неработавшего анализатора не считается отрицательным результатом;
- низкий риск нельзя присваивать только потому, что значимая часть анализаторов не выполнилась.

### 7.4. Критическая системная ошибка

При ошибке, делающей продолжение небезопасным или бессмысленным:

- обработка прекращается;
- очистка выполняется в завершающей секции;
- результат получает статус сбоя;
- пользователю не раскрываются внутренние пути, секреты и трассировки;
- подробности фиксируются в техническом журнале.

### 7.5. Ошибка удаления

Если временные данные не удалось удалить:

- ошибка удаления фиксируется отдельно от результата анализа;
- файл может быть перемещён в `runtime/quarantine/<analysis_id>/`;
- карантин не является штатным долговременным хранилищем;
- для карантина должны быть определены ограниченный доступ, TTL и повторная очистка;
- результат не должен ложно утверждать, что данные удалены.

## 8. Маршруты анализа по типу медиа

### 8.1. Изображения

Обязательная подготовка:

- безопасное чтение;
- технические параметры;
- метаданные;
- нормализованная рабочая копия.

Группы анализаторов-кандидатов:

- анализ метаданных;
- ELA;
- JPEG/DCT-анализ;
- copy-move detection;
- resampling detection;
- анализ шумовых несоответствий;
- анализ локальных аномалий;
- ML-детекторы манипуляций;
- ML-детекторы синтетических изображений.

Важно:

- отсутствие EXIF не является доказательством подделки;
- ELA не должна использоваться как самостоятельный окончательный детектор;
- повторное сохранение и пересылка могут создавать ложные признаки;
- конкретный набор первой версии имеет статус **OPEN**.

### 8.2. Аудио

Обязательная подготовка:

- безопасное декодирование;
- технические параметры;
- метаданные;
- нормализованное представление;
- фрагменты;
- спектральное представление при необходимости.

Группы анализаторов-кандидатов:

- анализ метаданных;
- временной анализ;
- спектральный анализ;
- признаки склейки;
- признаки повторного кодирования;
- признаки копирования фрагментов;
- детекторы синтетической речи;
- детекторы преобразования голоса.

Важно:

- короткая, шумная или сильно сжатая запись может быть неприменима для части методов;
- `confidence` модели не равен автоматически вероятности подделки файла;
- конкретный набор первой версии имеет статус **OPEN**.

### 8.3. Видео

Обязательная подготовка:

- параметры контейнера и потоков;
- метаданные;
- ключевые кадры или временные сегменты;
- аудиодорожка, если она присутствует;
- признаки времени и синхронизации.

Группы анализаторов-кандидатов:

- анализ метаданных;
- анализ кадров визуальными методами;
- временная согласованность;
- лицевые ориентиры;
- движение лица и мимики;
- синхронизация губ и речи;
- аудио-видео несоответствия;
- пространственно-временные ML-анализаторы;
- мультимодальные ML-анализаторы.

Важно:

- видео не загружается целиком в оперативную память без необходимости;
- обработка выполняется потоково или фрагментами;
- кадры могут переиспользовать анализаторы изображений;
- аудиодорожка может переиспользовать аудиоанализаторы;
- связанные признаки не должны бесконтрольно суммироваться несколько раз;
- конкретный набор первой версии имеет статус **OPEN**.

## 9. Результаты анализаторов и признаки

### 9.1. Результат анализатора

Каждый анализатор возвращает структурированный результат, содержащий как минимум смысловые категории:

- идентификатор анализатора;
- версию анализатора или модели;
- статус выполнения;
- применимость;
- длительность;
- техническое резюме;
- собственную оценку или `confidence`, если она действительно формируется методом;
- ошибки и предупреждения;
- локализацию результатов, если она доступна;
- исходные значения, необходимые модулю формирования признаков.

Точные поля определяются в `CONTRACTS.md`.

### 9.2. Признак

Признак — нормализованное основание, используемое риск-оценкой.

Признак должен сохранять:

- уникальный идентификатор;
- группу;
- серьёзность;
- источник-анализатор;
- версию источника;
- описание;
- локализацию;
- вклад в балл, если применимо;
- признак разрешённого critical override;
- связь с другими коррелирующими признаками, если требуется.

### 9.3. Канонические уровни серьёзности признаков

Чтобы не смешивать серьёзность признака с уровнем итогового риска, используются разные термины:

| Серьёзность признака | Смысл |
|---|---|
| `weak` | Косвенный технический признак, возможный при обычной обработке |
| `significant` | Признак возможной модификации или выраженной аномалии |
| `critical` | Сильный признак, удовлетворяющий отдельным проверенным условиям |

Итоговые уровни риска называются:

- `low`;
- `medium`;
- `high`.

Это разделение является **FIXED** и должно соблюдаться в коде и контрактах.

### 9.4. Связь признака с источником

Запрещено создавать признак без возможности установить:

- какой анализатор его сформировал;
- на какой версии анализатора;
- при каких параметрах;
- для какого участка файла;
- с каким статусом применимости;
- с какой собственной оценкой метода.

## 10. Риск-оценка

### 10.1. Общая модель

Итоговый риск формируется на основе набора признаков, а не на основе одного универсального детектора.

Модель может учитывать:

- серьёзность признака;
- надёжность и применимость анализатора;
- собственную оценку метода;
- совпадение результатов независимых анализаторов;
- корреляцию признаков;
- качество входных данных;
- полноту выполненного анализа;
- критические правила.

### 10.2. Балльная модель

Балльная модель допускается для MVP.

Проектный пример порогов:

- `low`: 0–29;
- `medium`: 30–60;
- `high`: 61 и выше.

Проектный пример не является валидированной шкалой.

До экспериментальной проверки:

- веса не считаются научно подтверждёнными;
- пороги не считаются откалиброванными;
- результат должен называться риск-оценкой, а не статистической вероятностью.

**Механизм баллов: CONDITIONAL.**  
**Конкретные веса и пороги: OPEN.**

### 10.3. Critical override

Критичный признак может повысить итоговый риск до `high` независимо от суммы баллов.

Однако право на critical override не возникает автоматически из высокого `confidence`.

Для применения правила должны быть явно определены:

- разрешённый тип признака;
- разрешённый анализатор и его версия;
- минимальные требования к входному качеству;
- минимальная оценка метода, если применима;
- успешный статус и применимость анализатора;
- отсутствие критических ошибок обработки;
- правила подтверждения другим методом, если это требуется;
- зафиксированная конфигурационная политика.

Точные правила имеют статус **OPEN** и должны быть определены до включения critical override в рабочую оценку.

Сам принцип critical override имеет статус **FIXED**.

### 10.4. Согласованность и корреляция

Совпадение независимых методов может усиливать доверие к признаку.

При этом запрещено бездумно складывать несколько результатов, основанных на одном и том же сигнале.

Например, результаты анализа лица, движения губ и аудиовизуальной синхронизации могут быть коррелированы. Модуль формирования признаков и риск-оценка должны предусматривать группировку, ограничение вклада или другое явно заданное правило.

**Конкретный алгоритм корреляции: OPEN.**

### 10.5. Полнота анализа

Итоговый результат должен различать:

- полноценный анализ;
- частичный анализ;
- невозможность анализа;
- системный сбой.

Необходимо отражать:

- какие анализаторы были запланированы;
- какие применимы;
- какие выполнены;
- какие отключены;
- какие завершились ошибкой;
- насколько это повлияло на итог.

Точное представление показателя полноты определяется в `CONTRACTS.md`.

### 10.6. Вероятность

Поле общей вероятности является допустимым, но не обязательным для MVP.

До появления валидированного способа калибровки:

- оно должно отсутствовать или иметь `null`;
- оно не копируется из отдельного анализатора;
- оно не формируется произвольным преобразованием суммы баллов;
- UI не должен показывать псевдоточную вероятность.

**Статус: OPEN.**

### 10.7. Формулировки результата

Допустимые формулировки:

- «выявлены признаки возможной модификации»;
- «обнаружены аномалии, требующие дополнительной проверки»;
- «существенных признаков доступными методами не выявлено»;
- «анализ выполнен частично»;
- «файл не удалось корректно обработать».

Недопустимые формулировки без экспертного подтверждения:

- «файл точно поддельный»;
- «файл гарантированно настоящий»;
- «личность подтверждена»;
- «атака доказана».

## 11. Итоговый результат и рекомендации

### 11.1. Машиночитаемый результат

Основной формат первой версии — JSON.

Результат должен включать смысловые блоки:

- версия схемы;
- идентификатор анализа;
- дата и время;
- статус;
- источник;
- сведения о файле;
- технические параметры;
- сведения о ходе обработки;
- результаты анализаторов;
- признаки;
- риск-оценка;
- полнота анализа;
- рекомендация;
- ошибки и предупреждения;
- сведения об удалении временных данных.

Точная JSON Schema принадлежит `CONTRACTS.md`.

### 11.2. Человекочитаемый результат

WebUI показывает представление той же доменной модели, а не рассчитывает результат повторно.

Пользователь должен видеть:

- понятный уровень риска;
- краткое объяснение;
- основные группы признаков;
- сведения о неполном анализе;
- рекомендацию;
- предупреждение, что результат не является окончательной экспертизой.

### 11.3. Рекомендации

Рекомендация зависит от риска и полноты анализа.

Возможные действия:

- принять результат к сведению;
- выполнить ручную проверку;
- проверить источник сообщения;
- запросить подтверждение по независимому каналу;
- повторить анализ при более качественном исходнике;
- передать данные специалисту ИБ;
- передать материал в систему расследования инцидентов.

Автоматическое удаление письма, блокировка пользователя или санкционирование бизнес-действий не входят в базовое ядро.

## 12. Хранение данных

### 12.1. Исходные и промежуточные данные

Исходные мультимедийные файлы не хранятся долговременно.

После анализа удаляются:

- исходный временный файл;
- нормализованные копии;
- извлечённые кадры;
- аудиофрагменты;
- спектрограммы;
- извлечённые аудиодорожки;
- другие промежуточные файлы.

**Статус: FIXED.**

### 12.2. Структура локального runtime

Первая версия использует локальную файловую систему:

```text
runtime/
├── temp/
│   └── <analysis_id>/
├── results/
├── logs/
└── quarantine/
```

Правила:

- рабочий каталог именуется только по `analysis_id`;
- оригинальное имя файла не используется как имя каталога;
- пользовательские значения не включаются в путь напрямую;
- пути формируются средствами приложения;
- `quarantine` используется только при сбое очистки.

### 12.3. Результаты анализа

Первая версия не использует отдельную СУБД.

Результат сохраняется как:

```text
runtime/results/<analysis_id>.json
```

Запись должна быть атомарной: сначала временный файл результата, затем безопасная замена целевого файла.

### 12.4. Условия перехода на SQLite

SQLite рассматривается при появлении требований:

- поиск по SHA-256;
- история анализов;
- фильтрация и сортировка;
- статистика;
- повторное использование результата;
- учёт пользователей;
- устойчивое хранение состояний долгих задач;
- большое количество JSON-файлов;
- конкурентная работа нескольких пользователей;
- необходимость транзакционной записи.

До появления таких требований SQLite не добавляется.

**Статус SQLite: CONDITIONAL.**

### 12.5. Политика хранения результатов

Открытые параметры:

- срок хранения JSON-результатов;
- срок хранения логов;
- максимальное число локальных результатов;
- очистка устаревших результатов;
- повторное использование результата по хэшу.

**Статус: OPEN.**

## 13. Журналирование

### 13.1. Назначение

Технический журнал используется для:

- диагностики;
- отслеживания жизненного цикла задачи;
- анализа производительности;
- фиксации ошибок;
- контроля очистки.

Он не заменяет итоговый JSON-результат.

### 13.2. Формат

Используется стандартный `logging` и формат JSON Lines.

Пример:

```text
runtime/logs/application.jsonl
```

Запись события по возможности содержит:

- `timestamp`;
- `level`;
- `event`;
- `analysis_id`;
- `module`;
- `analyzer_id`;
- `duration_ms`;
- `status`;
- `error_type`;
- безопасное сообщение.

Используется ротация по размеру с ограниченным количеством архивных копий.

### 13.3. Запрещённое содержимое логов

В журнале запрещено хранить:

- содержимое исходного файла;
- бинарные данные;
- извлечённые кадры;
- аудиофрагменты;
- пароли;
- API-токены;
- секреты;
- персональные данные без необходимости;
- пользовательские полные пути без диагностической необходимости;
- необработанные трассировки в пользовательском ответе.

## 14. Конфигурация

### 14.1. Формат

Основная конфигурация хранится в YAML и проверяется Pydantic-моделями.

Предполагаемые разделы:

```text
server
access_channels
limits
allowed_formats
validation
temporary_storage
preprocessing
analyzers
risk_assessment
result
error_handling
logging
external_systems
```

Точная схема определяется в `CONTRACTS.md`.

### 14.2. Секреты

Секреты хранятся только в:

- переменных окружения;
- локальном `.env`, исключённом из Git;
- другом отдельно согласованном защищённом механизме.

В репозиторий нельзя включать реальные токены и пароли.

### 14.3. Валидация конфигурации

При запуске система должна:

1. прочитать YAML;
2. прочитать переменные окружения;
3. собрать итоговую конфигурацию;
4. проверить типы и ограничения;
5. проверить обязательные каталоги и зависимости;
6. прекратить запуск с понятной ошибкой при критической некорректности.

### 14.4. Примеры не равны решениям

Значения в примере конфигурации не должны автоматически означать:

- что все перечисленные анализаторы реализуются в MVP;
- что все ML-модели загружаются;
- что интеграции с SIEM/DLP/SOAR включены;
- что проектные веса и пороги валидированы.

Для MVP рекомендуется отдельный минимальный `config.example.yaml`, содержащий только реально реализованные компоненты.

## 15. Безопасность обработки

### 15.1. Модель доверия

Все входные файлы считаются потенциально недоверенными.

### 15.2. Обязательные меры

- ограничение размера до полного ресурсоёмкого анализа;
- проверка расширения;
- проверка MIME-типа;
- проверка сигнатуры;
- проверка соответствия типов;
- безопасное декодирование;
- ограничение времени обработки;
- ограничение CPU, памяти и параллельности;
- безопасное формирование путей;
- отсутствие выполнения содержимого файла;
- обработка сбоев внешних декодеров;
- очистка временных данных;
- отсутствие секретов в логах;
- аутентификация WebUI;
- токен для API.

### 15.3. Внешние процессы

FFmpeg и другие внешние инструменты вызываются:

- без использования пользовательской строки как команды оболочки;
- через безопасный список аргументов;
- с ограничением времени;
- с контролем кода возврата;
- с ограниченным рабочим каталогом;
- без исполнения произвольных сценариев.

### 15.4. Персональные данные

Мультимедийные материалы могут содержать изображения лиц, голоса и другие чувствительные сведения.

Поэтому:

- минимизируется хранение;
- исходники удаляются;
- доступ к runtime ограничивается;
- содержимое не попадает в журнал;
- сохранение файла для расследования выполняется внешней защищённой системой, а не ядром по умолчанию.

### 15.5. Аутентификация

- WebUI должен предусматривать аутентификацию;
- точный механизм WebUI имеет статус **OPEN**;
- API использует токен;
- статический токен из переменной окружения допустим для MVP;
- управление выпуском, отзывом и сроком токенов относится к последующим требованиям;
- rate limiting добавляется после определения реального сценария интеграции.

## 17. Качество кода и тестирование

### 17.1. Общие требования

- команды и инструкции по возможности приводятся для PowerShell.

### 17.2. Обязательные группы тестов

- модульные тесты;
- интеграционные тесты;
- тесты API;
- тесты конфигурации;
- тесты валидации файлов;
- тесты сигнатур и несоответствия типов;
- тесты маршрутизации;
- тесты временного хранения;

### 17.3. Тестовые данные

Тестовые файлы должны:

- быть небольшими;
- иметь известное происхождение;
- быть разрешены для использования;
- не содержать конфиденциальных данных;

- создание `analysis_id`;
- проверку размера, расширения, MIME и сигнатуры;
- безопасное чтение;


Конкретные этапы и текущий статус определяются только в `ROADMAP.md`.

- резервное копирование служебных результатов;
- формат поставки;
- способ установки FFmpeg;
- требования к развёртыванию.

### 21.6. Интеграции

- почтовая система и протокол коннектора;
- SIEM;

- SOAR;
- правила отправки событий;
- форматы внешнего экспорта.

## 22. Неизменяемые инварианты

Без явного решения владельца проекта запрещено:

1. заменять риск-оценку бинарным вердиктом;
2. считать результат окончательной экспертизой;
3. использовать один универсальный детектор как всё ядро;
4. жёстко привязывать ядро к электронной почте;
5. включать почтовый коннектор внутрь ядра анализа;
6. автоматически распаковывать архивы;
7. автоматически извлекать мультимедиа из документов;
8. хранить исходные файлы долговременно;
9. считать отсутствие метаданных доказательством подделки;
10. запускать анализаторы до первичной проверки;
11. останавливать весь анализ из-за любого сбоя отдельного анализатора;
12. выдавать низкий риск при существенно неполном анализе без явного предупреждения;
13. терять связь признака с анализатором-источником;
14. копировать `confidence` анализатора в итоговую вероятность;
15. добавлять инфраструктуру без подтверждённой необходимости;
16. добавлять незафиксированные функции «заодно»;
17. размещать бизнес-логику в HTTP-маршрутах;
18. сохранять секреты или содержимое файлов в логах;
19. включать реальные анализируемые файлы, результаты, логи и веса моделей в Git;
20. считать проектные примеры финальными решениями.

## 24. Термины

**Анализатор** — независимый модуль, проверяющий файл или подготовленные данные по определённой группе признаков.

**Признак** — нормализованное основание, полученное из результата анализатора и используемое риск-оценкой.

**Риск-оценка** — объяснимый итог агрегирования признаков; не является окончательным доказательством подделки.

**Critical override** — правило повышения итогового риска до `high` при наличии разрешённого критичного признака и выполнении утверждённых условий.

**Полнота анализа** — характеристика того, какая часть запланированных и применимых проверок была успешно выполнена.

**WebUI** — серверный веб-интерфейс ручной загрузки и просмотра результата.

**API** — программный интерфейс передачи файла и получения машиночитаемого результата.

**Почтовый коннектор** — внешний компонент, извлекающий вложения из электронной почты и передающий их API.

**Временное хранилище** — изолированная рабочая область, существующая только на период анализа и очистки.

**Репозиторий результатов** — абстракция сохранения и получения итоговых структурированных результатов.

**Технический журнал** — поток диагностических событий; не является хранилищем результата или исходного файла.

**MIME-тип** — заявленный тип содержимого файла.

**Фактическая сигнатура** — тип файла, определяемый по его содержимому, а не только по имени.

**SHA-256** — контрольное хэш-значение файла, используемое для идентификации объекта анализа.

## 25. Краткая формула проекта

```text
недоверенный мультимедийный файл
→ безопасная первичная проверка
→ определение типа медиа
→ временное изолированное хранение
→ предварительная обработка
→ набор применимых анализаторов
→ нормализованные признаки
→ объяснимая риск-оценка с учётом полноты
→ рекомендация и отчёт
→ очистка временных данных
→ сохранение служебного результата и технического журнала
```

Ключевой смысл:

- система **не доказывает подделку**;
- система **оценивает риск и объясняет основания**;
- исходные файлы **не хранятся долговременно**;
- ядро **не зависит от конкретного канала поступления**;
- сначала реализуется **простой сквозной контур**, затем подключаются сложные анализаторы и интеграции.
