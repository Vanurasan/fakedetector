# Инструкции для ИИ-агента

## Обязательное чтение

Всегда читать `AGENTS.md`, `docs/PROJECT.md` и текущий этап/связанные задачи
`docs/ROADMAP.md`. Дополнительно читать относящиеся к задаче разделы:

- `docs/CONTRACTS.md` — интерфейсы, данные, предобработка и результаты;
- `docs/METHODS.md` — анализаторы и конкретные методы;
- `docs/REFERENCES.md` — происхождение, зависимости и внешние методы;
- `docs/CHANGELOG.md` — только когда нужны история или причины решений.

## Полномочия документов и задания

Документы владеют своими областями, без общего ранжирования:

| Документ | Область |
|---|---|
| `AGENTS.md` | Правила исполнения задач агентом и приёмки изменений |
| `docs/PROJECT.md` | Назначение, архитектура, границы, стек, продуктовые политики и инварианты |
| `docs/CONTRACTS.md` | Интерфейсы, модели, схемы, ошибки и общие контракты анализаторов/предобработки/результатов |
| `docs/METHODS.md` | Принятые конкретные криминалистические методы, применимость, измерения и пороги |
| `docs/REFERENCES.md` | Происхождение и лицензии внешних источников и компонентов |
| `docs/ROADMAP.md` | Этапы, macros/increments, статусы, owner gates, критерии завершения и следующая работа |
| `docs/CHANGELOG.md` | История принятых изменений и причин; не текущий нормативный источник |

`docs/research/` содержит исследовательские свидетельства, не production-контракты.
Код и тесты — свидетельства реализации; они не переопределяют канонические
решения. Расхождение документации и кода — drift для явного разрешения.
Противоречие между нормативными областями — `STOP / OWNER GATE`; молча выбирать
документ запрещено.

Задание задаёт точный scope, ожидаемые branch/HEAD, требования инкремента и явные
owner gates/deltas. Оно не становится автоматически постоянным источником истины.
Изменение канонического решения должно быть прямо разрешено заданием и отражено
в документе владельца области в составе того же принимаемого изменения.
Иначе конфликт задания и документации нужно сообщить владельцу.

## Baseline и Git

До изменений отдельно проверить текущую ветку, HEAD (сравнить с ожидаемым,
если задан) и `git status --short --untracked-files=all`. Рабочее дерево должно
быть чистым либо точно соответствовать явно заданному ожидаемому состоянию.
При несовпадении baseline — `STOP / BLOCKED`: сообщить различие владельцу,
не исправлять состояние через Git mutations.

Агенты никогда не выполняют Git mutations: запрещены `git add`, `commit`,
`push`, `pull`, `merge`, `rebase`, `reset`, `clean`, `switch`, `checkout`,
создание/переключение/удаление веток, операции изменения тегов и переписывание
истории. Разрешена только read-only диагностика; использовать `git --no-pager`
для команд с возможным pager. Все staging/commit и другие Git mutations
выполняет владелец.

## Scope и решения владельца

- Перед существенными изменениями изучить релевантные документы, код и тесты;
  кратко описать план. Выполнять только запрошенную задачу в контексте ROADMAP.
- Не добавлять незапрошенные функции, зависимости, поля, абстракции или
  compatibility paths; не выполнять попутный рефакторинг.
- Изменения зависимостей, публичных контрактов и архитектуры требуют явного
  разрешения в scope и закрытия соответствующего owner gate.
- Не принимать `OPEN`-решения и не превращать `EXAMPLE` или имя кандидата в
  контракт. Для реализации нового метода обязателен gate из `docs/METHODS.md`.
- Неразрешённое необходимое решение владельца — `STOP / OWNER GATE` для зависимой
  работы. Независимую разрешённую работу можно продолжать.
- Не ослаблять assertions или safety boundaries ради прохождения тестов.
  Собственные дефекты и падающие проверки в scope исправлять; они не `BLOCKED`.
- Read-only audit не разрешает исправлений: проблемы оформлять как findings;
  отрицательный результат — `AUDIT FAIL`. Неподтверждённая из-за инструмента
  проверка — `OWNER_VERIFY_REQUIRED`, не дефект проекта.
- Не раскрывать секреты и не включать в Git медиафайлы, модели или runtime-данные.

## Проверки и приёмка

**AGENT SELF-REPORT IS NOT OWNER ACCEPTANCE.**

Обычный цикл: реализация агентом → focused tests → полный обязательный quality
barrier репозитория (`uv run poe check`; требования качества — `docs/PROJECT.md`
§17, команды также в `README.md`) → изменения остаются unstaged → владелец
получает и изучает полный diff → вердикт владельца `PASS` или `REMEDIATE` →
только владелец выполняет staging/commit.

Для docs-only задачи более узкие проверки допустимы, если это прямо разрешено
заданием. Всегда выполнить `git diff --check`, просмотреть фактический diff и
итоговый status. Отдельно проверить scope creep, случайное расширение API,
дублирование/устаревший код, лишние зависимости/config/schema и временные хвосты.
Зелёные тесты не заменяют этот просмотр.

Одна важная проверяемая команда — один terminal invocation. При потере вывода
повторить только эту команду. В финальном отчёте указать изменённые файлы,
проверки и их результаты, ограничения и итоговый Git status. Не заявлять
завершение этапа без критериев ROADMAP и приёмки владельца.

## Package verification и strict certification

Installed/package verification из dirty source tree допустима как development
verification, но **никогда не называется strict certification**. Строгая
сертификация требует определённых репозиторием условий clean committed SHA
(см. `docs/PROJECT.md` §16.2.1 и `scripts/verify_release.py`). При сертификации
installed artifact запрещён скрытый fallback на editable install или source tree.

## Graphify — REBUILD_POLICY

Graphify — только вспомогательный инструмент, не production dependency и не
package authority. `graphify-out/` и все generated/cache/memory/interpreter/root
данные остаются ignored/untracked, не коммитятся и не входят в source distributions.
Устаревший граф не является архитектурным доказательством.

Пересборка выполняется только вручную и явно после существенных изменений
структуры модулей, composition, импортов, lifecycle, каталога анализаторов,
release tooling или нормативных архитектурных контрактов; не после каждой правки.
Фиксировать source/build SHA либо эквивалентный fingerprint. `CURRENT` допустим
только при совпадении provenance с исходниками, иначе — `STALE`. Проверять охват
модулей, пути/символы, provenance и версию генератора, репрезентативные связи.

## Документация и review-артефакты

- Содержательные дополнения русскоязычных документов писать по-русски.
- Обновлять документ владельца решения; не дублировать спецификацию в других
  документах. ROADMAP отражает фактический статус и gates, CHANGELOG — существенные
  принятые изменения поведения, архитектуры, контрактов, технологий или governance.
- `.diff`, audit scratch files и временные отчёты хранить вне репозитория,
  не коммитить. Полный diff для owner review обычно сохраняется в
  `%USERPROFILE%\Desktop`, если владелец не указал другое место.
- Tracked исследовательские материалы по политике `docs/research/README.md`
  отличаются от временных review-артефактов и не означают принятие метода.
- Материалы owner review должны охватывать все предполагаемые изменения,
  включая intended untracked-файлы. `git diff HEAD` / `git diff` не включают
  untracked-файлы и сами по себе недостаточны, если итоговый
  `git status --short --untracked-files=all` содержит предполагаемые `??` entries.
  До объявления готовности к owner review проверить итоговый status и убедиться,
  что каждый такой файл явно включён в review bundle или иначе предоставлен
  владельцу полностью. О непредусмотренных untracked-файлах сообщить владельцу,
  не игнорировать их молча. Не решать это через staging: Git mutations выполняет
  только владелец.
