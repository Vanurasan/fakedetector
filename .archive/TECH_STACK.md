# TECH_STACK.md

## 1. Назначение документа

Документ фиксирует технологический стек программного проекта МДКП.

Стек выбирается с учетом следующих требований:

* анализ изображений, аудио и видео;
* возможность подключения классических и ML-анализаторов;
* локальный запуск;
* наличие WebUI;
* наличие программного API;
* минимальное количество инфраструктурных компонентов;
* отсутствие долговременного хранения исходных мультимедийных файлов;
* сохранение только результатов анализа и технических журналов;
* возможность постепенного расширения проекта;
* удобство сопровождения с помощью ИИ-агента.

Технологии, не указанные в настоящем документе, не должны добавляться без отдельного обоснования.

# 2. Основной язык разработки

## 2.1. Python

Основной язык проекта:

```text
Python 3.12
```

Python используется для:

* серверного приложения;
* обработки файлов;
* реализации бизнес-логики;
* предварительной обработки изображений, аудио и видео;
* подключения ML-моделей;
* выполнения анализаторов;
* расчета риск-оценки;
* формирования отчетов;
* автоматизированного тестирования.

## 2.2. Причины выбора

Python выбран по следующим причинам:

* широкий выбор библиотек компьютерного зрения;
* развитая экосистема обработки аудио;
* наличие библиотек для обработки видео;
* совместимость с PyTorch;
* доступность готовых ML-моделей;
* большое количество реализаций методов цифровой криминалистики;
* удобство интеграции внешних анализаторов;
* возможность быстро создавать прототипы;
* хорошая поддержка со стороны ИИ-инструментов разработки.

## 2.3. Ограничения

Python не рассматривается как единственно возможный язык для всех будущих компонентов.

При необходимости отдельные ресурсоемкие анализаторы могут позднее реализовываться на:

* C++;
* Rust;
* другом производительном языке.

Такие компоненты должны подключаться через четко определенный внутренний интерфейс.

Переписывание всего проекта на другой язык без подтвержденной технической необходимости не допускается.

## 2.4. Версия Python

Используется ветка Python 3.12.

Причины:

* зрелая версия языка;
* высокая совместимость с библиотеками анализа данных и ML;
* поддержка современного синтаксиса и типизации;
* меньший риск несовместимости библиотек, чем при немедленном переходе на новейшую версию Python.

Точная patch-версия фиксируется в файле:

```text
.python-version
```

# 4. Серверное приложение

## 4.1. FastAPI

Основной веб-фреймворк:

```text
FastAPI
```

FastAPI используется для:

* приема файлов через API;
* реализации WebUI;
* проверки входных параметров;
* возврата результатов анализа;
* предоставления документации API;
* реализации служебных маршрутов;
* обработки ошибок на уровне HTTP.

## 4.2. ASGI-сервер

Сервер приложения:

```text
Uvicorn
```

Uvicorn используется как ASGI-сервер для локального запуска и разработки.

На первом этапе отдельный reverse proxy не используется.

## 4.3. Архитектурное ограничение

FastAPI является внешним слоем приложения.

Бизнес-логика не должна размещаться непосредственно в HTTP-маршрутах.

Маршрут должен:

1. принять запрос;
2. проверить параметры;
3. вызвать прикладной сервис;
4. преобразовать результат в HTTP-ответ.

Модули анализа не должны зависеть от FastAPI.

# 8. Хранение исходных и временных файлов

## 8.1. Исходные файлы

Исходные мультимедийные файлы не хранятся долговременно.

Файл размещается во временном каталоге только на период анализа.

После завершения обработки должны удаляться:

* исходный файл;
* нормализованные копии;
* извлеченные кадры;
* аудиофрагменты;
* спектрограммы;
* аудиодорожки, извлеченные из видео;
* другие промежуточные файлы.

## 8.2. Локальное временное хранилище

Для первой версии используется локальная файловая система.

Рекомендуемая структура:

```text
runtime/
├── temp/
│   └── <analysis_id>/
├── results/
├── logs/
└── quarantine/
```

Каталог `quarantine` допускается только для файлов, которые не удалось удалить автоматически.

Он не используется для штатного долговременного хранения файлов.

## 8.3. Правила именования

Рабочие каталоги должны использовать внутренний идентификатор анализа:

```text
analysis_id
```

Оригинальное имя файла не должно использоваться как имя рабочего каталога.

Пути должны формироваться только средствами приложения.

Пользовательские значения не должны напрямую включаться в системный путь.

# 9. Хранение результатов анализа

## 9.1. Первая версия

На первом этапе отдельная база данных не используется.

Результат каждого анализа сохраняется как отдельный JSON-файл:

```text
runtime/results/<analysis_id>.json
```

JSON-файл должен содержать:

* версию схемы;
* идентификатор анализа;
* дату и время;
* источник поступления;
* SHA-256 хеш файла;
* тип файла;
* технические параметры;
* статусы обработки;
* результаты анализаторов;
* выявленные признаки;
* риск-оценку;
* рекомендации;
* сведения об ошибках;
* статус удаления временных данных.

## 9.2. Причины отказа от СУБД в первой версии

На первом этапе проекту не требуется:

* сложная многопользовательская работа;
* редактирование связанных объектов;
* транзакционная бизнес-логика;
* сложные выборки;
* полнотекстовый поиск;
* централизованное сетевое хранилище;
* высокая частота конкурентной записи.

Использование PostgreSQL, SQLAlchemy и системы миграций на первом этапе создало бы дополнительную сложность без обязательной функциональной пользы.

## 9.3. Абстракция хранилища

Несмотря на файловое хранение, прикладной код не должен напрямую записывать JSON-файлы из разных модулей.

Должен существовать единый интерфейс:

```text
ResultRepository
```

Минимальные операции:

```text
save(result)
get(analysis_id)
exists(analysis_id)
list_recent(limit)
```

Первая реализация:

```text
JsonFileResultRepository
```

Это позволит позднее заменить файловое хранение без изменения модулей анализа и риск-оценки.

## 9.4. Условия перехода на SQLite

SQLite подключается при появлении хотя бы одного из требований:

* поиск результата по хешу;
* просмотр истории анализов;
* фильтрация по уровню риска;
* сортировка по времени;
* формирование статистики;
* повторное обнаружение ранее проверенного файла;
* учет пользователей;
* хранение статусов долгих задач;
* одновременная работа нескольких пользователей;
* значительное количество JSON-файлов;
* необходимость гарантированной атомарной записи структурированных данных.

## 9.5. Возможная вторая реализация

При необходимости создается:

```text
SQLiteResultRepository
```

SQLite используется как локальная встроенная база данных.

Отдельный сервер базы данных для этого не требуется.

## 9.6. ORM и миграции

На первом этапе не используются:

* SQLAlchemy;
* Alembic;
* PostgreSQL;
* MySQL;
* MongoDB;
* Redis как постоянное хранилище.

Решение об ORM принимается только после подтверждения необходимости реляционной модели данных.

# 10. Журналирование

## 10.1. Стандартный механизм

Для журналирования используется стандартный модуль Python:

```text
logging
```

Дополнительная библиотека журналирования на первом этапе не требуется.

## 10.2. Формат

Основной машиннообрабатываемый формат:

```text
JSON Lines
```

Одна строка файла соответствует одному событию.

Пример имени:

```text
runtime/logs/application.jsonl
```

## 10.3. Ротация

Используется ротация логов:

* по размеру файла;
* с ограниченным числом архивных копий.

## 10.4. Содержание записи

Запись журнала должна по возможности включать:

* timestamp;
* level;
* event;
* analysis_id;
* module;
* analyzer_id;
* duration_ms;
* status;
* error_type;
* message.

## 10.5. Ограничения

В логах запрещается хранить:

* содержимое исходного файла;
* бинарные данные;
* извлеченные кадры;
* аудиофрагменты;
* токены доступа;
* пароли;
* персональные данные без необходимости;
* полный путь пользователя, если он не требуется для диагностики.

## 10.6. Разделение логов и результатов

Технический лог не является хранилищем результатов анализа.

Результат анализа сохраняется отдельно в JSON-файле.

Лог предназначен для диагностики работы программы.

# 14. Машинное обучение

## 14.1. Основной фреймворк

Основной ML-фреймворк:

```text
PyTorch
```

PyTorch используется только для анализаторов, которым необходимы нейросетевые модели.

## 14.2. Правило подключения моделей

ML-модель должна подключаться как самостоятельный анализатор.

Она не должна быть жестко встроена в:

* WebUI;
* API;
* модуль приема файлов;
* модуль риск-оценки.

Каждый ML-анализатор должен реализовывать общий контракт анализатора.

## 14.3. Вычислительное устройство

Система должна поддерживать:

```text
CPU
CUDA — при наличии совместимого GPU
```

Выбор устройства должен определяться конфигурацией и фактической доступностью оборудования.

## 14.4. Загрузка моделей

Весовые файлы моделей:

* не должны автоматически попадать в Git;
* должны храниться в отдельном каталоге;
* должны иметь контрольную сумму;
* должны иметь указанную версию;
* должны иметь зафиксированный источник;
* должны иметь сведения о лицензии.

## 14.5. Ограничения

До выбора конкретных анализаторов не фиксируются:

* точная версия PyTorch;
* версия CUDA;
* перечень моделей;
* формат хранения весов;
* требования к видеопамяти.

Эти параметры определяются после проверки оборудования и совместимости выбранных моделей.

# 15. Очередь и параллельная обработка

## 15.1. Первая версия

В первой версии внешний брокер задач не используется.

Не используются:

* Celery;
* RabbitMQ;
* Kafka;
* Redis Queue.

Управление задачами реализуется внутри приложения с ограничением параллельности.

Допускаются:

* `asyncio`;
* очереди стандартной библиотеки;
* `concurrent.futures`;
* отдельные процессы для CPU-нагруженных операций.

## 15.2. Причины

Внешний брокер задач преждевременно усложнит:

* установку;
* настройку;
* отладку;
* переносимость;
* демонстрацию программы.

## 15.3. Условия перехода к внешней очереди

Внешняя очередь рассматривается при появлении требований:

* распределенная обработка;
* несколько рабочих узлов;
* гарантированное восстановление задач;
* длительная обработка большого количества файлов;
* независимое масштабирование анализаторов;
* выполнение задач на отдельных GPU-серверах.

Тестовые мультимедийные файлы должны:

* быть небольшими;
* не содержать конфиденциальных данных;
* иметь известное происхождение;
* быть разрешенными для использования;
* храниться отдельно от рабочих файлов.

Большие наборы данных и веса моделей не включаются в основной Git-репозиторий.

## 16.4. Покрытие

Для измерения покрытия используется:

```text
pytest-cov
```

Процент покрытия не должен быть единственным критерием качества тестирования.

# 26. Принципы выбора новых технологий

Новая технология может быть добавлена только при наличии конкретной потребности.

Перед добавлением необходимо ответить на вопросы:

1. Какую существующую проблему решает технология?
2. Почему эту проблему нельзя разумно решить текущим стеком?
3. Какие новые зависимости появляются?
4. Как технология повлияет на установку и сопровождение?
5. Как она повлияет на безопасность обработки файлов?
6. Как она повлияет на тестирование?
7. Существует ли более простой вариант?
8. Можно ли удалить технологию позднее без переработки ядра?

Принцип проекта:

```text
Не добавлять инфраструктуру заранее.
Добавлять ее только после появления подтвержденной необходимости.
```

# 29. Статус решений

## Принято

* основной язык — Python 3.12;
* управление зависимостями — uv;
* серверный слой — FastAPI;
* WebUI — серверные HTML-шаблоны;
* конфигурация — YAML с валидацией;
* исходные файлы хранятся только временно;
* результаты первой версии сохраняются в JSON;
* технические логи сохраняются в JSONL;
* PostgreSQL не используется;
* SQLAlchemy и Alembic не используются на первом этапе;
* Redis и внешняя очередь задач не используются;
* Docker не является обязательным для старта;
* ML-анализаторы подключаются поэтапно.

## Условно принято

* PyTorch как основной ML-фреймворк;
* SQLite как возможное хранилище второй версии;
* HTMX для частичного обновления WebUI;
* ExifTool для расширенного анализа метаданных.

## Требует уточнения

* конкретные анализаторы первой версии;
* состав ML-моделей;
* использование GPU;
* механизм аутентификации;
* сроки хранения результатов;
* формат поставки программы.
