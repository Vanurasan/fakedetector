# 1. Назначение системы

Система предназначена для анализа мультимедийных файлов на признаки искусственного создания или модификации.

Основной сценарий применения — проверка мультимедийных вложений электронной почты.

Поддерживаемые типы мультимедийных файлов:

* изображения;
* аудио;
* видео.

Система не устанавливает факт подделки окончательно.

Результатом работы системы является риск-оценка файла.

Итоговый результат должен содержать:

* вероятность;
* уровень риска;
* пояснение;
* рекомендацию по дальнейшим действиям.

Основная архитектурная идея:

* система принимает мультимедийный файл;
* выполняет первичную проверку;
* определяет тип медиа;
* выбирает соответствующий путь обработки;
* запускает набор анализаторов;
* агрегирует выявленные признаки;
* формирует риск-оценку;
* возвращает результат пользователю или внешней системе;
* удаляет временные файлы после завершения анализа.

# 2. Общая архитектура

Система проектируется как модульный инструмент анализа мультимедийных файлов.

Логическая архитектура состоит из следующих уровней:

1. Уровень приема данных.
2. Уровень первичной проверки.
3. Уровень маршрутизации.
4. Уровень управления обработкой.
5. Уровень временного хранения.
6. Уровень предварительной обработки.
7. Уровень специализированного анализа.
8. Уровень риск-оценки.
9. Уровень формирования результата.
10. Уровень журналирования и хранения служебных сведений.
11. Уровень конфигурации.

## 2.1. Модуль WebUI

### Назначение

Ручная загрузка мультимедийного файла пользователем через браузер.

### Ответственность

* прием файла от пользователя;
* передача файла в ядро анализа;
* отображение человекочитаемого результата анализа.

### Взаимодействие

* получает файл от пользователя;
* передает файл в модуль приема данных;
* получает результат от модуля формирования результата.

---

## 2.2. Модуль API

### Назначение

Автоматизированный прием файлов от внешних систем и возврат результата в машиночитаемом формате.

### Ответственность

* прием файла через программный интерфейс;
* проверка доступа по токену;
* применение ограничения частоты запросов, если включено;
* возврат JSON-отчета внешней системе.

### Взаимодействие

* получает файл от внешних систем;
* передает файл в модуль приема данных;
* получает JSON-отчет от модуля формирования результата;
* возвращает результат внешней системе.

---

## 2.3. Модуль приема данных

### Назначение

Единая точка входа для файлов, поступающих через WebUI или API.

### Ответственность

* получение файла;
* первичная регистрация задачи анализа;
* передача файла на проверку допустимости.

### Взаимодействие

* получает файл из WebUI или API;
* передает файл в модуль первичной проверки;
* создает задачу анализа.

---

## 2.4. Модуль первичной проверки

### Назначение

Проверка файла до запуска анализа.

### Ответственность

* проверка расширения файла;
* проверка MIME-типа;
* проверка фактической сигнатуры файла;
* проверка размера файла;
* проверка возможности безопасного чтения;
* проверка соответствия заявленного и фактического типа;
* расчет SHA-256 хэша файла;
* отклонение неподдерживаемых файлов.

### Взаимодействие

* получает файл от модуля приема данных;
* передает допустимый файл в модуль маршрутизации;
* возвращает ошибку при недопустимом файле.

---

## 2.5. Модуль маршрутизации по типу медиа

### Назначение

Определение типа мультимедийного файла и выбор пути обработки.

### Ответственность

* определение типа медиа;
* выбор маршрута обработки для изображения;
* выбор маршрута обработки для аудио;
* выбор маршрута обработки для видео;
* отклонение неподдерживаемого типа файла.

### Взаимодействие

* получает проверенный файл от модуля первичной проверки;
* передает файл в соответствующий блок предварительной обработки;
* передает сведения о типе медиа в задачу анализа.

---

## 2.6. Модуль управления задачами

### Назначение

Управление выполнением задач анализа.

### Ответственность

* постановка задачи анализа в очередь;
* контроль параллельной обработки;
* управление статусом задачи;
* фиксация времени начала и завершения анализа.

### Взаимодействие

* получает задачу от модуля маршрутизации;
* взаимодействует с временным хранилищем;
* запускает предварительную обработку;
* запускает анализаторы через модуль управления анализом.

---

## 2.7. Модуль временного хранения

### Назначение

Хранение исходного и промежуточных файлов только на период анализа.

### Ответственность

* временное размещение исходного файла;
* временное размещение промежуточных файлов;
* применение TTL;
* удаление исходного файла после анализа;
* удаление промежуточных файлов после анализа.

### Взаимодействие

* получает файл от модуля управления задачами;
* предоставляет файл модулям предварительной обработки;
* предоставляет промежуточные данные анализаторам;
* передает статус удаления в отчет или журнал.

---

## 2.8. Модуль предварительной обработки изображений

### Назначение

Подготовка изображения к анализу.

### Ответственность

* извлечение метаданных изображения;
* нормализация изображения для анализа;
* подготовка данных для анализаторов изображений.

### Взаимодействие

* получает изображение из временного хранилища;
* передает подготовленные данные анализаторам изображений.

---

## 2.9. Модуль предварительной обработки аудио

### Назначение

Подготовка аудиофайла к анализу.

### Ответственность

* извлечение метаданных аудио;
* разбиение аудио на фрагменты;
* построение спектрограммы;
* подготовка данных для аудиоанализаторов.

### Взаимодействие

* получает аудио из временного хранилища;
* передает подготовленные данные аудиоанализаторам.

---

## 2.10. Модуль предварительной обработки видео

### Назначение

Подготовка видеофайла к анализу.

### Ответственность

* извлечение технических параметров видео;
* извлечение метаданных видео;
* извлечение ключевых кадров;
* извлечение аудиодорожки;
* подготовка данных для видеоанализаторов;
* подготовка кадров для анализаторов изображений;
* подготовка аудиодорожки для аудиоанализаторов.

### Взаимодействие

* получает видео из временного хранилища;
* передает кадры, аудиодорожку и технические параметры в соответствующие анализаторы.

---

## 2.11. Модуль управления анализаторами

### Назначение

Организация запуска анализаторов в зависимости от типа файла и конфигурации.

### Ответственность

* определение списка активных анализаторов;
* запуск анализаторов изображений;
* запуск анализаторов аудио;
* запуск анализаторов видео;
* сбор результатов анализаторов;
* фиксация ошибок анализаторов;
* продолжение анализа при сбое отдельного анализатора, если это возможно.

### Взаимодействие

* получает подготовленные данные от модулей предварительной обработки;
* обращается к конфигурации активных анализаторов;
* передает результаты анализаторов в модуль формирования признаков.

Источник:

* пользователь.

Канал:

* браузер;
* WebUI.

Тип данных:

* мультимедийный файл.

Преобразования:

1. Файл принимается WebUI.
2. Файл передается в модуль приема данных.

4. Файл проходит первичную проверку.

15. Пользователь получает результат.
16. Временные файлы удаляются.
17. Служебные сведения сохраняются в журнале.

1. Внешняя система отправляет мультимедийный файл через API.

3. API передает файл в модуль приема данных.
4. Создается задача анализа.
5. Выполняется первичная проверка файла.
6. Если файл недопустим, API возвращает ошибку.
7. Если файл допустим, определяется тип медиа.
8. Файл размещается во временном хранилище.
9. Задача ставится в очередь.

16. Временные файлы удаляются.
17. Служебные сведения сохраняются в журнале.

## 5.3. Обработка недопустимого файла

1. Файл поступает через WebUI или API.
2. Выполняется проверка расширения.
3. Выполняется проверка MIME-типа.
4. Выполняется проверка фактической сигнатуры.

6. Выполняется проверка безопасного чтения.
7. Если файл не соответствует требованиям, обработка прекращается.
8. Пользователь или внешняя система получает сообщение об ошибке.
9. Служебные сведения о попытке обработки могут быть зафиксированы в журнале.

---

## 5.4. Обработка ошибки анализатора

1. Анализатор запускается в рамках задачи анализа.
2. Анализатор завершает работу с ошибкой.
3. Ошибка фиксируется.
4. Система определяет, возможно ли продолжить анализ.
5. Если продолжение возможно, остальные анализаторы продолжают работу.
6. Ошибка включается в отчет.
7. При необходимости анализ маркируется как неполный.
8. Результат формируется с учетом доступных данных.

1. Анализаторы формируют результаты.

3. Один из признаков определяется как критичный.
4. Модуль риск-оценки рассчитывает сумму баллов.
5. Модуль риск-оценки проверяет наличие критичного признака.
6. Применяется critical override.
7. Итоговый уровень риска устанавливается как high.
8. В отчете фиксируется факт применения critical override.
9. Формируется пояснение.
10. Формируется рекомендация.

# 10. Ограничения архитектуры

## 10.1. Ограничения входных данных

* Поддерживаются только изображения, аудио и видео.
* Архивы не анализируются автоматически.
* Документы не анализируются автоматически.
* Контейнерные форматы не анализируются автоматически.
* Файл должен быть передан на анализ напрямую.
* Тип файла должен соответствовать допустимым форматам.
* MIME-тип должен соответствовать фактической сигнатуре.
* Размер файла ограничивается конфигурацией.

---

## 10.2. Ограничения хранения

* Исходные файлы не хранятся долговременно.
* Временные файлы удаляются после анализа.
* Промежуточные данные удаляются после анализа.
* В журнале сохраняются только служебные сведения.

---

## 10.3. Ограничения результата

* Результат не является доказательством подделки.
* Результат является риск-оценкой.
* Результат зависит от качества входного файла.
* Результат зависит от сжатия, перекодирования, разрешения и длительности записи.
* Результат зависит от используемых анализаторов и моделей.

---

## 10.4. Ограничения риск-оценки

* Пороги low, medium, high обсуждались как проектный пример.
* Веса признаков не валидированы.
* Критичный признак может повысить риск до high.
* Один слабый признак не должен формировать высокий риск.
* Отсутствие метаданных не является доказательством подделки.

---

## 10.5. Ограничения интеграции

* Конкретная интеграция с SIEM не спроектирована.
* Конкретная интеграция с DLP не спроектирована.
* Конкретная интеграция с SOAR не спроектирована.
* Почтовый коннектор не спроектирован подробно.
* Схемы обмена с внешними системами не определены.

---

## 10.6. Ограничения реализации

* Прототип не реализован.
* API не реализован.
* WebUI не реализован.
* Очередь задач не реализована.
* Временное хранилище не реализовано.
* JSON-отчет не реализован.
* YAML-конфигурация не реализована.
* Журналирование не реализовано.
* Анализаторы не подключены.
* Экспериментальная проверка не выполнена.
